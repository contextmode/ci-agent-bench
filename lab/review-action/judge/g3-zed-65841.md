# Review of PR #65841: `agent_ui: Preserve input through ACP reconnect and replay`

I read the diff only. I did not build it or run the tests. The PR is already merged and has one approval, so treat the items below as follow-ups.

## Summary
The PR snapshots data-only recovery state when an ACP session loses observation. That state is the composer draft, the queue, the submission content and receipt evidence, and the session context. The state is kept across `LoadError`, authentication gates and retries. It is restored into the new thread only after a successful full replay. Retry no longer falls back to history-less `resume_session` while recovering. The UI gains **Copy Saved Input** (JSON) and **Discard Saved Submissions**.

The design is careful. Recovery holds only cloneable data (`SubmissionState` now derives `Clone` and `Serialize`). The queue comes back paused. Nothing is resent automatically. The tests cover failure, authentication, repeated retry, opaque content and receipt metadata.

## Potential bugs and issues

1. **Generic error can overwrite a specific one** (`conversation_view.rs`, the `AcpThreadEvent::LoadError` arm).
   - That arm now calls `thread.handle_connection_lost(cx)`. When the thread was still observable, this emits `ConnectionLost`.
   - The `ConnectionLost` handler calls `handle_load_error` with the generic "Agent connection lost. Reconnect to restore the conversation."
   - The original `LoadError(error)` is handled in the same arm. The queued `ConnectionLost` event may then run afterwards and replace the real error with the generic text.
   - Please check the ordering. If the generic text wins, add a test that asserts the original error message survives. Alternatively, skip the emit when the loss was triggered by a `LoadError`.

2. **Recovery is captured in only one place.**
   - `set_server_state` snapshots only when the new state is `ServerState::LoadError`.
   - `ConnectionLost` goes through `handle_load_error`, which presumably ends up there. The authentication path and any other route that drops the root view without a `LoadError` state depend on that holding.
   - A short comment, or a single choke point that is clearly the only entry, would guard against a regression. `snapshot_recovery` returns `None` unless `uses_reported_activity() && is_observation_closed()`, so a missed route silently loses input.

3. **Saved submissions can pile up and never clear.**
   - `saved_submissions` is only cleared by the manual Discard button. The "Copy Saved Input / Discard" bar stays visible indefinitely after a successful reconnect.
   - `has_saved_input()` also blocks idle eviction (`cleanup_retained_threads`) and counts the draft as having content in `agent_panel.rs`. A stale saved copy pins a thread in memory for as long as the panel lives.
   - Consider an upper bound or a lifetime tied to the session.
   - Repeated disconnects append to `saved_submissions` via `extend`. The PR says import is idempotent with tombstones, but I only see the test covering a two-record case. A test with three or more disconnect cycles would confirm there are no duplicates.

4. **Discard has no confirmation.** It irreversibly clears the only copy of user input, including receipt evidence for submissions in an uncertain state. The tooltip explains it, but a one-click destructive action beside Copy is easy to hit. A confirmation, or an "undo until next render" step, would be safer.

5. **Tracked buffers are lost on export.** `QueuedMessageRecovery.tracked_buffers` is restored in memory but is not in the JSON. That is probably fine, since they are entities. The export is described as lossless, so note the gap in the docs or the tooltip.

6. **Clipboard export size and sensitivity.** Content blocks can include images or embedded resources, which serialize as base64. `to_string_pretty` could produce a very large string for the clipboard. That is acceptable for an explicit user action. Consider compact serialization for large payloads.
