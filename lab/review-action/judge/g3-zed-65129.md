# REVIEW A

**Review of PR #65129: Fix `shift-enter` in search bar for JetBrains keymap**

The PR is already merged and was approved. The fix is small and well targeted, and I found no blocking issues.

**What it does**
- It changes the context for `search::SelectPreviousMatch` on `shift-enter` from `BufferSearchBar` to `BufferSearchBar && !in_replace > Editor`.
- The new context selects the query editor inside the search bar. That is deeper in the context tree, so it takes precedence over the `Editor && mode == auto_height` binding to `NewlineBelow`.
- The Linux and macOS keymaps get the same change, which keeps them consistent.

**Code quality and correctness**
- The `!in_replace` guard looks correct. Shift-Enter in the replace field is not hijacked, so it can still insert a newline there. I did not check whether the replace field has other `shift-enter` bindings.
- I did not look at other keymap files. If the Windows JetBrains keymap or other keymaps have the same pattern, they may need the same fix. The diff touches only `linux/` and `macos/`, so a quick check of whether a Windows file exists would be worthwhile.
- The JSON change is minimal and fits the existing context syntax.

**Test coverage**
- The new test `test_shift_enter_selects_previous_match_with_jetbrains_keymap` is a good regression test. It loads the default keymap and then the JetBrains keymap in the same order as production, so precedence is tested realistically.
- It asserts the key behaviors: no newline is inserted into the query, and the active match wraps from the first to the last.
- It only exercises the macOS-or-Linux asset that `BaseKeymap::JetBrains.asset_path()` resolves to for the host platform. This is acceptable.
- It does not cover the `in_replace` case, where shift-enter should still insert a newline. A negative test would lock in the `!in_replace` behavior.

**Style against CLAUDE.md**
- The test uses `.unwrap()` in several places, for example `load_asset_allow_partial_failure(...).unwrap()` and `editor.clone().unwrap()`. CLAUDE.md asks to avoid this, though `unwrap` is common in Zed tests and acceptable there. Using `.expect(...)` or `?` would be a bit more consistent.

**Performance and security**
- There are no performance or security concerns. The change is keymap context data plus a test.

**Process note**

# REVIEW B

# Review of PR #65129: JetBrains keymap `shift-enter` in the search bar

The PR is already merged. I read the diff and description but did not build it or run the test. I also didn't check the other context strings in the keymaps, so some points below are unverified.

## Summary
The JetBrains keymaps bound `shift-enter` to `search::SelectPreviousMatch` under the context `BufferSearchBar`. A more specific `Editor && mode == auto_height` binding to `editor::NewlineBelow` shadowed it. The PR changes the context to `BufferSearchBar && !in_replace > Editor`. This is more specific, so it wins. The change is small, targeted, and applied consistently to both the macOS and Linux files.

## Code quality
- The context change is minimal and matches the problem description.
- The commit message and PR description are clear, and the release note is correctly worded.

## Potential issues
1. **Replace field behavior is unverified and untested.** The new `!in_replace` predicate excludes the replace editor.
   - There, `shift-enter` still falls through to the previous `NewlineBelow` binding if that editor is `auto_height`.
   - JetBrains' replace field uses `shift-enter` for something different, so this may be fine or even intended.
   - It would help to say so in the PR or to test it.
2. **Precedence depends on `>` specificity.** The fix works because a `BufferSearchBar > Editor` path is deeper than `Editor && mode == auto_height`.
   - That could silently break if the context tree changes, for example if the query editor is no longer a direct descendant.
   - The new test guards against this, which is good.
3. **Other search bars may still have the same problem.** The project search and thread search bars may need equivalent treatment. The description mentions a similar thread-search test, so that may already be handled. I didn't check.
4. **Other keymaps may be affected.** The same shadowing could apply to other base keymaps that bind `shift-enter` in the search bar (for example the default keymap or Sublime/VS Code variants). I didn't check.

## Tests
The new test, `test_shift_enter_selects_previous_match_with_jetbrains_keymap`, is a real end-to-end keystroke test. Loading the default keymap and then the JetBrains keymap in the same order as production is a good way to catch precedence bugs. It also asserts that no newline is inserted into the query and that the active match wraps to the last match.

Style points against `CLAUDE.md`:
- The test uses `.unwrap()` on `load_asset_allow_partial_failure(...)` and on `editor.clone().unwrap()`, and `.expect(...)` elsewhere. Panics are common in tests, but the guidelines prefer avoiding them. Returning `anyhow::Result` from the test would be cleaner.
- The keymap loading block is long and likely duplicates the setup in the similar thread-search test. A shared helper such as `load_jetbrains_keymap(cx)` would reduce the duplication.
- There is no test for the replace-field case or for the macOS vs Linux keymap files. Both files load via `BaseKeymap::JetBrains.asset_path()`, so the test only covers the file for the platform it runs on.
- The comments explain why, which fits the guidelines. The "test precondition" assertion messages are fine.

## Performance and security
Neither applies. This is a static keymap and test change.

## Verdict
This is a good, minimal fix. I'd suggest a small follow-up to clarify or test the replace-field behavior, and to deduplicate the keymap-loading setup.
