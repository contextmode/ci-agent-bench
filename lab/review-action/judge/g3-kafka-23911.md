+    private static final int PARTITIONS = 2;
+    private static final int RECORDS_PER_PARTITION = 8000;
+    private static final int MAX_POLL_RECORDS = 100;
+
+    public ShareConsumerFairnessTest(ClusterInstance cluster) {
+        super(cluster);
+    }
+
+    @ClusterTest
+    public void testPartitionsWithDeepBacklogAreServedFairly() throws Exception {
+        String topic = "fairness";
+        String groupId = "fairness-group";
+        createTopic(topic, PARTITIONS, 1);
+        try (Producer<byte[], byte[]> producer = createProducer()) {
+            for (int i = 0; i < RECORDS_PER_PARTITION; i++) {
+                for (int p = 0; p < PARTITIONS; p++) {
+                    producer.send(new ProducerRecord<>(topic, p, null, null, "value".getBytes()));
+                }
+            }
+            producer.flush();
+        }
+        alterShareAutoOffsetReset(groupId, "earliest");
+
+        Map<Integer, Integer> recordsByPartition = new TreeMap<>();
+        // The records by partition at the moment the first partition has been consumed completely.
+        Map<Integer, Integer> recordsWhenFirstPartitionCompleted = null;
+        int totalRecords = PARTITIONS * RECORDS_PER_PARTITION;
+        int consumedRecords = 0;
+        try (ShareConsumer<byte[], byte[]> consumer = createShareConsumer(groupId, Map.of(
+            ConsumerConfig.MAX_POLL_RECORDS_CONFIG, String.valueOf(MAX_POLL_RECORDS),
+            ConsumerConfig.SHARE_ACQUIRE_MODE_CONFIG, "record_limit"))) {
+            consumer.subscribe(Set.of(topic));
+            // Consume all the records, the test timeout fails the test if some records are not delivered.
+            while (consumedRecords < totalRecords) {
+                for (ConsumerRecord<byte[], byte[]> record : consumer.poll(Duration.ofMillis(500))) {
+                    consumedRecords++;
+                    int partitionRecords = recordsByPartition.merge(record.partition(), 1, Integer::sum);
+                    if (partitionRecords == RECORDS_PER_PARTITION && recordsWhenFirstPartitionCompleted == null) {
+                        recordsWhenFirstPartitionCompleted = new TreeMap<>(recordsByPartition);
+                    }
+                }
+            }
+        }
+
+        assertEquals(Map.of(0, RECORDS_PER_PARTITION, 1, RECORDS_PER_PARTITION), recordsByPartition);
+        for (int p = 0; p < PARTITIONS; p++) {
+            // Both partitions have a deep backlog, hence neither should have been starved while the other was
+            // being served, i.e. each has a meaningful share of the records when the first partition completes.
+            int recordsOfPartition = recordsWhenFirstPartitionCompleted.getOrDefault(p, 0);
+            assertTrue(recordsOfPartition * 5 >= RECORDS_PER_PARTITION,
+                "Partition " + p + " was starved, records by partition when the first partition completed: "
+                    + recordsWhenFirstPartitionCompleted);
+        }
+    }

# REVIEW A

**Review of apache/kafka#23911: Track share fetch offset metadata per DelayedShareFetch instead of SharePartition**

The PR is already merged, with two approvals. I read the diff and spot-checked `DelayedShareFetch`. I didn't run any tests.

**Summary**

The PR moves the cached `LogOffsetMetadata` (used for the minBytes estimate) out of `SharePartition` and into a per-request `HashMap<TopicIdPartition, CachedFetchOffsetMetadata>` in `DelayedShareFetch`. This is the same lifetime that `DelayedFetch` gives its `FetchPartitionStatus`.

The approach is sound. A cache entry can no longer go stale across requests. That lets the PR delete `resetFetchOffsetMetadataForRemoteFetchPartitions`, the `OffsetMetadata` inner class, and two lock-guarded methods on `SharePartition`. `SharePartition` gets simpler and there is one less thing to keep consistent under its lock.

**Code quality**

- Using a private `record CachedFetchOffsetMetadata` is a good fit and is clearer than the old mutable class.
- `fetchOffsetMetadata()` treats an offset mismatch or a null metadata as a miss. That keeps the old semantics, and it also covers the case where the remote-fetch reset used to be needed.
- Nit: the `// Visible for testing.` setter `updateFetchOffsetMetadataCache` is package-private and only tests use it. That is acceptable.
- Nit: the PR body says "which requires resets". The sentence is garbled and was baked into the squash commit message.

**Potential bugs and concurrency**

- `fetchOffsetMetadataCache` is a plain `HashMap`. I'm reasonably confident it is safe, but the PR doesn't say why.
  - `DelayedOperation.tryComplete` runs under the operation lock (`safeTryComplete`).
  - The async read callback is explicitly documented as running under that lock, in the comments near lines 448–450.
  - I did not fully trace whether `onComplete` or `processFetchResultAndComplete` ever touches the cache outside that lock. From the diff it only reads and writes in `maybeReadFromLog`, `maybeUpdateFetchOffsetMetadata` and `isMinBytesSatisfied`, all on the `tryComplete` path.
  - A short comment on the field stating the "guarded by the operation lock" assumption would help future maintainers.
- The cache is never invalidated within a request. It is keyed by fetch offset, so if the offset advances the entry misses naturally. If records are released and the fetch offset moves back to the same value, the old metadata is reused. The log has not changed position for a given offset, so this should be fine. The PR description says this scenario is now handled.
- The old cache effectively persisted across requests. Now each new `DelayedShareFetch` does at least one log read before it can evaluate minBytes. That is likely negligible next to the stale-state bugs it removes, but it is a small behavior change.

- Removing the `SharePartition` read and write lock acquisitions from the hot path is a small gain.
