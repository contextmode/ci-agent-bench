+    private static final int PARTITIONS = 2;
+    private static final int RECORDS_PER_PARTITION = 8000;
+    private static final int MAX_POLL_RECORDS = 100;
+
+    public ShareConsumerFairnessTest(ClusterInstance cluster) {
+        super(cluster);
+    }
+
+    @ClusterTest
+    public void testPartitionsWithDeepBacklogAreServedFairly() throws Exception {
+        String topic = "fairness";
+        String groupId = "fairness-group";
+        createTopic(topic, PARTITIONS, 1);
+        try (Producer<byte[], byte[]> producer = createProducer()) {
+            for (int i = 0; i < RECORDS_PER_PARTITION; i++) {
+                for (int p = 0; p < PARTITIONS; p++) {
+                    producer.send(new ProducerRecord<>(topic, p, null, null, "value".getBytes()));
+                }
+            }
+            producer.flush();
+        }
+        alterShareAutoOffsetReset(groupId, "earliest");
+
+        Map<Integer, Integer> recordsByPartition = new TreeMap<>();
+        // The records by partition at the moment the first partition has been consumed completely.
+        Map<Integer, Integer> recordsWhenFirstPartitionCompleted = null;
+        int totalRecords = PARTITIONS * RECORDS_PER_PARTITION;
+        int consumedRecords = 0;
+        try (ShareConsumer<byte[], byte[]> consumer = createShareConsumer(groupId, Map.of(
+            ConsumerConfig.MAX_POLL_RECORDS_CONFIG, String.valueOf(MAX_POLL_RECORDS),
+            ConsumerConfig.SHARE_ACQUIRE_MODE_CONFIG, "record_limit"))) {
+            consumer.subscribe(Set.of(topic));
+            // Consume all the records, the test timeout fails the test if some records are not delivered.
+            while (consumedRecords < totalRecords) {
+                for (ConsumerRecord<byte[], byte[]> record : consumer.poll(Duration.ofMillis(500))) {
+                    consumedRecords++;
+                    int partitionRecords = recordsByPartition.merge(record.partition(), 1, Integer::sum);
+                    if (partitionRecords == RECORDS_PER_PARTITION && recordsWhenFirstPartitionCompleted == null) {
+                        recordsWhenFirstPartitionCompleted = new TreeMap<>(recordsByPartition);
+                    }
+                }
+            }
+        }
+
+        assertEquals(Map.of(0, RECORDS_PER_PARTITION, 1, RECORDS_PER_PARTITION), recordsByPartition);
+        for (int p = 0; p < PARTITIONS; p++) {
+            // Both partitions have a deep backlog, hence neither should have been starved while the other was
+            // being served, i.e. each has a meaningful share of the records when the first partition completes.
+            int recordsOfPartition = recordsWhenFirstPartitionCompleted.getOrDefault(p, 0);
+            assertTrue(recordsOfPartition * 5 >= RECORDS_PER_PARTITION,
+                "Partition " + p + " was starved, records by partition when the first partition completed: "
+                    + recordsWhenFirstPartitionCompleted);
+        }
+    }

# REVIEW A

# Review of PR 23911: track share fetch offset metadata per `DelayedShareFetch`

I read the diff only. I didn't build the code or run any tests. The PR is already merged with two approvals, so these are post-merge notes.

## Summary
The PR moves the fetch-offset-metadata cache from `SharePartition` (long-lived, lock-guarded) into `DelayedShareFetch` (scoped to one request). That removes cross-request staleness and the `resetFetchOffsetMetadataForRemoteFetchPartitions` workaround. It also deletes `SharePartition.OffsetMetadata` and its locked accessors, which simplifies the code. The design follows how `DelayedFetch` uses `FetchPartitionStatus`, and it is sound.

## Code quality
- The `CachedFetchOffsetMetadata` record is clean. The null check in `fetchOffsetMetadata(...)` correctly keeps the old "null metadata means miss" behavior.
- `updateFetchOffsetMetadataCache` is package-private and marked "Visible for testing". That is acceptable, but `tryComplete` tests could instead seed the cache through the normal read path.
- The `fetchOffsetMetadata` local variable in `isMinBytesSatisfied` now shares a name with the new method. It compiles, but it is slightly confusing.
- The commit message says "which requires resets". Reading it as "required resets" makes the rationale clearer.

## Potential issues
1. **Thread safety.** `fetchOffsetMetadataCache` is a plain `HashMap`. The old state sat behind the `SharePartition` lock. This is safe only if every access happens inside `tryComplete`, which runs under the `DelayedOperation` lock, or on a single thread. Please confirm `onComplete` and the remote and async-fetch callback paths never touch it. A short comment on the field stating this assumption would help.
2. **Removed remote-storage reset.** The old reset handled a partition that was read locally in `tryComplete` but needed a remote fetch in `onComplete`. Now the cache dies with the request, so the "empty response on every retry" loop can't recur. However, if `tryComplete` is invoked again within the same operation after the remote switch, the cached entry could still say "local". I believe this can't happen, because `onComplete` completes the operation. Worth a test if there isn't one.
3. **Weaker minBytes optimization across requests.** Each new `DelayedShareFetch` starts with a cold cache, so the first `tryComplete` of every request does a log read for metadata. The PR accepts this trade-off. A short note on the cost for high-fan-in groups would be nice.

## Performance
- Dropping the `SharePartition` read and write lock acquisitions on this path is a small win.
- The cost is the extra cold-cache read per request, as noted above.

## Security
No concerns. There are no input-handling or authorization changes.

## Tests
- `ShareConsumerFairnessTest` is useful. Its fairness assertion (each partition has at least 20% of its records when the first partition completes) is deliberately loose, which should keep it from being flaky.
- It writes 16k records one send at a time and consumes them with 500 ms polls under a 600 s timeout. That could be slow on CI. Consider whether a smaller data set gives the same signal.
- `DelayedShareFetchTest` and `SharePartitionManagerTest` were updated to the new API, but I didn't read those hunks. Ideally they cover these cases:
  - a cache hit with a matching offset;
  - a miss when the offset differs;
  - the "released record previously fetched" case from the PR description, to check it no longer waits for the timeout.

## Verdict
This is a good simplification that removes a source of stale state. The main follow-up is to document, or verify, the single-threaded access assumption on the new `HashMap`.

# REVIEW B

# Review of apache/kafka PR #23911: track share fetch offset metadata per `DelayedShareFetch`

The PR is already merged, with two approvals. I read the `DelayedShareFetch` and `SharePartition` diffs in full. I did not read the test diffs line by line, and I did not build or run anything. My view is that the change is sound and I have no blocking concerns.

## Summary
`SharePartition` used to cache `LogOffsetMetadata` for the fetch offset. That cache outlived the request that filled it. A partition could be read and then trimmed from the response, or its request could fail. In either case the cache stayed valid even though the fetch offset had not moved. The PR moves the cache into `DelayedShareFetch` as a `HashMap<TopicIdPartition, CachedFetchOffsetMetadata>`, so it lives only as long as the request. This mirrors how `DelayedFetch` uses `FetchPartitionStatus`.

## Code quality
- **Simpler design.** Request-scoped state removes the need for `SharePartition.OffsetMetadata`, `updateFetchOffsetMetadata`, `fetchOffsetMetadata` and the locking around them. Share-partition state no longer depends on what an earlier request left behind.
- **Reset hack removed.** `resetFetchOffsetMetadataForRemoteFetchPartitions` existed only to undo stale cache state when a partition switched from local to remote fetch between `tryComplete` and `onComplete`. With a per-request cache that case cannot persist across requests, so deleting it is correct.
- **Small, clear types.** The private `record CachedFetchOffsetMetadata(long offset, LogOffsetMetadata offsetMetadata)` is documented. The lookup keeps the same semantics as before: it returns empty if the entry is missing, the offset differs, or the metadata is null.
- **Naming.** The `fetchOffsetMetadata(...)` helper has the same name as the local variable `fetchOffsetMetadata` in `isMinBytesSatisfied`. That is legal Java but slightly confusing. A name like `cachedFetchOffsetMetadata(...)` would read better. This is a nit.
- **Test hook.** `updateFetchOffsetMetadataCache` is package-private and marked "Visible for testing", which follows convention.

## Potential issues
1. **Thread safety.** `fetchOffsetMetadataCache` is a plain `HashMap`. `tryComplete` runs under the `DelayedOperation` lock, so the usual path is safe. `maybeUpdateFetchOffsetMetadata` and the async or remote-fetch paths may also touch the cache. If any of them can run in a completion callback on another thread, the map needs protection. Please confirm that every access happens under the operation lock, or use a `ConcurrentHashMap`. The old code was protected by the `SharePartition` lock, so this is a small regression in guarantees if there is a gap.
2. **Cache lifetime.** The cache is only an optimization inside purgatory retries. If a request completes and a new `DelayedShareFetch` is created, its first `tryComplete` does one extra log read per partition. This is the intended trade-off. The new `ShareConsumerFairnessTest` and the PR note about releases waiting for timeout suggest it is a net win.
3. **Retained metadata.** The map holds `LogOffsetMetadata` only for the life of the request, so I see no memory concern.

## Performance
- Retries in purgatory still avoid re-reading the log.
- The `SharePartition` read/write lock is no longer taken on the `minBytes` estimation path, which removes some contention.
- The behavioral fix is the main gain. Requests no longer wait for the full timeout because of stale cache entries.

## Security
Nothing relevant. The change only affects in-memory bookkeeping and adds no new inputs or external surface.

## Test coverage
- `ShareConsumerFairnessTest` is a new integration test checking that two partitions with deep backlogs are both served under `record_limit` acquire mode. That is a good end-to-end check for the starvation scenario.
- `DelayedShareFetchTest` and `SharePartitionManagerTest` were updated to use the new cache API. The diff there is large (about 430 lines), which fits the API move.
- Suggested additions:
  - A unit test showing the cache is not reused by a second `DelayedShareFetch` for the same partition.
  - A test for a partition that is read but trimmed, confirming the next request re-reads the log.
  - If any paths are multi-threaded, a concurrency test.

## Conventions
- The title uses the `MINOR:` prefix, which is allowed.
- The description explains what changed and why.
- The `SharePartition` removals are non-public classes, so no KIP is needed.

**Verdict:** a clean refactor that fixes a real correctness and latency problem. The only follow-up I'd suggest is confirming that all cache accesses are single-threaded or lock-protected.
