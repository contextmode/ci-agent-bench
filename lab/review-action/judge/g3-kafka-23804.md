# REVIEW A

# Review of PR #23804: KAFKA-21181 NOT_COORDINATOR from a stale transaction coordinator cache (4.3 backport)

This is a backport of #23630. It is already merged and was approved by jolshan. I found no CLAUDE.md in the checkout, so I used the surrounding Kafka Scala conventions. I read the diff only and did not run the build or tests.

## Summary
`TransactionStateManager.getTransactionState` and `putTransactionStateIfNotExists` now serve a cache entry only if the local replica still leads the `__transaction_state` partition at the entry's coordinator epoch. Otherwise they return `NOT_COORDINATOR`. This closes the window between losing leadership and `onResignation` unloading the cache. In that window a TV2 `EndTxn(COMMIT)` could get a fatal `INVALID_TXN_STATE` instead of a retriable error.

## Production change
The change is small, well commented and placed correctly: a guard case in the existing `match` ahead of the normal cache path.

- **Correctness.** Returning `NOT_COORDINATOR` is the right fix, because clients treat it as retriable and rediscover the coordinator. The same guard covers `putTransactionStateIfNotExists`, so InitProducerId no longer allocates a producer ID or adds an entry on a partition the broker no longer leads. One test checks that this path doesn't call `generateProducerId()`.
- **Epoch equality (`==`).** This relies on the cache entry's `coordinatorEpoch` always being the partition leader epoch captured at load time. The strict equality is the intended fencing: a newer epoch means a reload is pending. Please confirm that nothing bumps the partition's leader epoch while the same broker stays leader. If something does, the broker would return `NOT_COORDINATOR` until the reload happens. That is safe but could add transient unavailability. The new test `leader again at a newer epoch` documents this behaviour as intended.
- **Performance.** The extra cost is one `onlinePartition` map lookup plus two cheap accessors per lookup. That is negligible compared with the existing locking and log appends. `new TopicPartition` is allocated on each call, which is minor.
- **Locking.** `isCoordinatorFor` runs inside the existing read-lock path. `Partition.isLeader` and `getLeaderEpoch` read volatile state and don't take `Partition`'s locks. I don't see a lock-ordering risk.
- **Race.** The check and the cache read aren't atomic. Leadership can still be lost just after the check. That is unavoidable here, and the append path fences with the coordinator epoch and the log append itself. The window is far smaller than before.

## Tests
Coverage is good. It includes unit tests in `TransactionStateManagerTest` and coordinator-level tests for EndTxn, VerifyPartitions, AddPartitions and InitProducerId. It also covers loss of leadership between the log append and its callback.

Suggestions, none blocking:
- **Mock plumbing.** The `Answer`-based `Partition` mocks are verbose. The same pattern is duplicated in `AbstractCoordinatorConcurrencyTest` and `TransactionStateManagerTest`. A small shared test helper would reduce that. Using the `defaultAnswer` to survive `reset(replicaManager)` is clever but easy to break, so the comment helps.
- **Concurrency-test mock.** The concurrency base class previously returned a fresh `mock(classOf[Partition])`, whose `isLeader` is false. It now returns a cached mock keyed only by leader epoch. That is fine, but `leaderPartitions` is keyed on `Integer`, so there is some boxing.
- **Test state.** In `testInitProducerIdReturnsNotCoordinator...`, the test restores `leaderEpochOf` partway through to run its final assertion. Splitting that into a separate step or helper would make it clearer.
- **Missing coverage.** I didn't see tests for the other callers of `getTransactionState`, such as transaction expiration and `handleListTransactions` or `DescribeTransactions`. Check that returning `NOT_COORDINATOR` from the shared lookup is the right behaviour for those too. It likely is.

## Security
No concerns.

## Verdict
The fix is sound, minimal and well tested, and the backport is faithful to trunk. The only follow-ups are the optional test cleanups above and confirming that the leader epoch can't change without a coordinator reload.
