# REVIEW A

**Review of #121020: "Don't always duplicate the image when validating the format"**

The PR is already merged and approved. I read the diff and checked its callers in `texture_storage.cpp`. I didn't build or run anything.

**Summary:** `_validate_texture_format` used to call `p_image->duplicate()` on every call. It now starts with `image = p_image` and only duplicates inside the "not supported, reconvert" branches. Two small helpers, `duplicate_and_convert` and `duplicate_decompress_and_convert`, wrap the duplicate-then-convert steps. On the common path, where the format is supported, this skips a full copy of the texture data. That is a real saving for large textures and for streaming uploads.

**Correctness**
- I found no bugs. Every `image->convert(...)` and `image->decompress()` that mutated the local copy was replaced with a helper that works on a duplicate. The original `p_image` is therefore never mutated.
- In the ASTC cases, `decompress()` used to run before `r_format` was set. The new code sets `r_format` first and then calls the helper. That's harmless, and the ordering is now consistent.
- I checked how callers use the returned image:
  - `texture_2d_create`, the layered create and update paths, `_texture_2d_update` and the 3D paths only read from it (`get_format()`, `get_data()`).
  - If they now get the caller's own `Image`, nothing is written to it.
  - The PR description flags this behaviour change itself, and it looks safe.
- `texture_drawable_create` passes a freshly created temporary image, so aliasing doesn't matter there.
- One pre-existing oddity, not from this PR: `texture.validated_format = image->get_format()` uses the unvalidated `image`, not `valid_image`.

**Style and quality**
- The helpers are file-local `static` functions, which is appropriate.
- Consolidating the repeated decompress/convert pairs reduces duplication.
- `const Image::Format original_format` and the `switch (original_format)` cleanup are good.
- The comment has a double space after the period ("format.  If"). That is a trivial nit.
- The `image` local is now only reassigned in fallback branches. The decompress-first naming is slightly verbose, but it is clear.

**Performance:** This is a clear win on the supported-format path, with no extra cost on the fallback path. A possible future improvement is a fast path for formats that never need conversion.

**Security:** No concerns. This is internal refactoring with no new input handling.

**Test coverage:** The PR adds no tests. That is understandable, since it's a renderer-internal change that is hard to unit test. A cheap regression guard would be a test or assertion that a texture created from an `Image` doesn't modify the source image's data or format. This matters more now that the source can be returned directly.

**Verdict:** LGTM. The change is small, safe and well-motivated. The aliasing risk is called out in the description and I found no caller affected by it.

**Summary:** `_validate_texture_format` no longer calls `p_image->duplicate()` up front. It starts with `image = p_image` and duplicates only in the branches that convert, through two small helpers, `duplicate_and_convert` and `duplicate_decompress_and_convert`. This avoids a full image copy on the common path where the format is already supported. The PR is already merged and approved. I read the diff and the callers, but the middle of the diff was truncated in my output, so I did not read every branch.

### Correctness
- **Callers only read the returned image.** I checked every call site in `texture_storage.cpp`:
  - `texture_2d_initialize` (line 995) only calls `get_format()` and `get_data()`.
  - The layered initializer (line 1089) only calls `get_format()` and `get_data()`.
  - `texture_2d_placeholder`/drawable creation (line 1352) never mutates `valid_image`.
  - `_texture_2d_update` (line 1649) only calls `get_data()`.
  - The 3D path (line 1191) was not confirmed in the shown output, but it looks like the same read-only pattern.
  
  So dropping the always-duplicate behavior looks safe. The PR description's concern about callers that depend on getting a copy doesn't apply to the call sites I read.
- **Old and new conversion semantics match.** Each branch that used to call `image->convert(...)` on the copy now does `image = duplicate_and_convert(p_image, ...)`. The compressed branches that decompressed first now call the decompress variant. The function still returns a valid image in every case.
- **Source image is now never mutated.** Previously the copy absorbed the conversion. Now the conversion happens on a fresh duplicate, so the caller's image is untouched. This is equivalent.

### Code quality
- The helpers are `static` file-local functions, which suits the style. `const Image::Format original_format` and `switch (original_format)` are small cleanups.
- Naming is clear. The helpers could carry a short comment saying they always copy, so nobody later passes an already-owned image through them.
- The comment "Assume we have a supported format..." is helpful. The inconsistent spacing after the period (two spaces) is minor, since Godot comments usually use one.
- Some branches have a nested if/else that picks between two conversions, such as RGBA16 and RGBAF. Both branches duplicate, so only one copy is made per call. That's fine.

### Performance
- This is a clear win for the common case. It saves one full image allocation and memcpy per texture upload, and it matters most for large textures and for streaming (#113429). Mipmapped images benefit most because the copy includes all levels.
- In the unsupported-format path there is still one duplicate plus one convert. `convert` itself may allocate again, but that cost was already there.

### Potential issues
- **Aliasing:** `image` now aliases the caller's image on the fast path. If a future caller mutates the returned image, it will silently change the user's data. A doc comment on the declaration in `texture_storage.h`, such as "may return `p_image` itself; do not modify", would guard against that.
- **Threading:** if a caller holds the returned `Ref` while another thread modifies the source, the old copy no longer protects it. The texture upload path is synchronous, so this is probably fine.
- **Pre-existing, not from this PR:** at line ~1352 `texture.validated_format = image->get_format()` uses `image` rather than `valid_image`. It looks like a latent inconsistency, though it's harmless here because that format is already supported.

### Security
No concerns. There are no new inputs or size calculations, and nothing about bounds changes.

### Test coverage
- The PR adds no tests. Godot has few rendering-server unit tests, so this is understandable.
- I'd suggest manual or visual checks on two cases:
  - A driver or format that is unsupported, such as RGB8 or compressed formats on hardware lacking support, to exercise the conversion paths.
  - A supported format, to confirm the source image is unchanged after upload.
- An optional test could create a texture from an `Image`, then check the source image's data and format are unchanged afterward.

### Verdict
Looks good. It's a small, low-risk optimization and the logic is sound. The one follow-up I'd suggest is documenting in the header that the returned image may alias the input.
