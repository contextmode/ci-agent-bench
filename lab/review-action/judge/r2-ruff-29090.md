+### Tuple subclasses
+
+Expanding the possible element types of a tuple subclass preserves its class identity. A class
+pattern matching that subclass is exhaustive, including when it appears inside a sequence pattern.
+
+```py

# REVIEW A

**Review of PR #29090: preserve tuple subclass identity during type expansion**

The PR is already merged and approved. I read the diff but did not build it or run the tests. Overall the change is small, targeted and sensible. My comments are below, with blockers separated from non-blocking points.

**Blockers:** none found.

**Non-blocking**

1. **Unexplained branch in `type_expansion.rs`.** The condition `instance.own_tuple_spec(db).is_some()` selects between returning the plain tuple and intersecting it with the subclass. The comment only covers the `else` branch. A reader can't tell why a class that has its own tuple spec skips the intersection. Presumably `ty` is then a plain tuple, or a spec-carrying type whose identity is already preserved, but the comment should say so. It would also help to give an example, such as `class P(NamedTuple)` versus `tuple[bool]` itself.

2. **Work done inside the Cartesian-product closure.** `IntersectionType::from_two_elements(db, env, ty, expanded)` runs once per product element. That can be as many as the expansion cap. The `own_tuple_spec` check is loop-invariant, so compute it once before the `.map`. Each intersection also has to be simplified and interned, which costs more than building a plain tuple. For large products on subclasses, check that the extra Salsa interning is acceptable. A quick benchmark or a note in the PR would help.

3. **Behavioural risk in downstream consumers.** Expanded elements are now `Point & tuple[Literal[True]]` rather than `tuple[Literal[True]]`. Anything that inspects expansion results and assumes a bare tuple instance could change. That includes diagnostic rendering, reachability narrowing, and `reveal_type` output after overload expansion. The tests cover the match and overload paths. They don't cover diagnostics that print the expanded type, for example an overload failure on `Point` that mentions the expansion.

4. **Test gaps.**
   - There is no case with a generic or specialized tuple subclass, such as `class Foo(tuple[int, bool])` or `class Bar[T](tuple[T, T])`.
   - There is no case for a non-`@final` subclass. `TupleSubclass` is final, so the final-class path isn't contrasted with the non-final one. A non-final subclass in a `case Sub():` pattern would show that exhaustiveness isn't over-claimed.
   - There is no case for a variadic tuple subclass (`tuple[int, ...]`). I didn't confirm whether that path expands at all.
   - There is no case where a subclass has its own tuple spec, which is the first branch of the new `if`. That branch is currently untested.
   - There is no case near the expansion limit.

5. **mdtest style, per `AGENTS.md`.**
   - The overload test has `reveal_type` assertions only. That is fine.
   - In `match.md`, the "Tuple subclasses" section holds two scenarios: the exhaustive cases, and the guard/refutable negatives. They are separated by prose, which is acceptable. The negative cases don't pair with a statement that they have no diagnostic. The `# no diagnostic` convention on the positive cases is followed, but those comments sit on the `def` lines.
   - The new overload section places its stub in `overloaded.pyi` and then imports it. A short inline `def` with `@overload` in a `py` block might be simpler. That is a minor point.

6. **PR description.** It is clear and describes the behavior. It doesn't mention the intersection mechanism's impact on the displayed type, or the performance consideration in point 2.

**Positives**
- The fix is minimal and sits at the right layer, in expansion itself. It avoids special-casing `match`.
- The tests cover both the match and overload-resolution paths, plus negative cases (guard, refutable attribute pattern).
- The PR carries the `bug` and `ty` labels, and the title uses the `[ty]` prefix, as the conventions require.

# REVIEW B

**Review of PR #29090: [ty] Preserve tuple subclass identity during type expansion**

The PR is already merged and approved. The fix is sound and the tests are good. I have a few non-blocking points.

**What it does**

`expand_type` used to rebuild tuple subclasses such as `NamedTuple` as plain `tuple[...]`, which lost the class identity. It now intersects each expanded tuple with the original type, `ty & tuple[...]`. `own_tuple_spec` is `Some` only for a plain tuple, so plain tuples are unaffected.

**Blockers**

None.

**Non-blocking points**

1. **Comment placement** (`type_expansion.rs`, new closure). The `own_tuple_spec(db).is_some()` check is in the per-product closure. It does not depend on the product element, so it is re-evaluated for every combination. Hoisting it above `.map` as a `let` would be cheaper and clearer. The cost is small, but the product can reach the Cartesian-product limit.

2. **Comment clarity.** The comment "The element types describe only the tuple base" is correct but terse. It would help to say that a plain `tuple[...]` has no subclass identity (`own_tuple_spec` is `Some`), so no intersection is needed in that case. It would also help to give the intended Python example, for instance `Point(NamedTuple)` expanding to `Point & tuple[Literal[True]]` and `Point & tuple[Literal[False]]`.

3. **Intersection simplification risk.** `IntersectionType::from_two_elements` can reduce or collapse to `Never`. For example, if a final subclass has a fixed tuple spec that is disjoint from the expanded element types, the result is `Never`. That is probably correct, but the tests don't exercise it. A case with a `@final` subclass of `tuple[bool]` in overload expansion would show that nothing collapses unexpectedly. The match test covers `@final class TupleSubclass(tuple[bool])`, but the overload test does not.

4. **Overload test coverage** (`overloads.md`).
   - `by_element(value)` is expected to give `int | str`. That shows `Point & tuple[Literal[True]]` still matches `tuple[Literal[True]]`, which is good.
   - There is no test for a generic tuple subclass (`class Foo[T](tuple[T, T])`). Its `own_tuple_spec` and specialization could behave differently.
   - There is no test for a tuple subclass with its own extra fields or a variadic base.

5. **Match tests** (`match.md`).
   - The `# no diagnostic` comments on the `def` lines follow the repo convention. They sit on the signature, not the match, which is fine.
   - The negative cases (`guarded`, `refutable`) are useful.
   - A non-final plain `tuple` subclass is not covered. There, a subclass of `Point` might not match `case Point()` exhaustively. The pattern should still be exhaustive because subclasses are instances of `Point`. A test would pin that down.

6. **Performance.** Each expansion now builds an intersection, which is interned in Salsa. For large expansions of tuple subclasses this adds interned types. The limit on the Cartesian product bounds it, so it is acceptable. No ecosystem or performance numbers are mentioned in the PR. A quick primer or benchmark run would confirm there is no regression.

**Security**

No concerns. This is internal type-checker logic with no trust boundary changes.

**Conventions**

- The new code follows the repo style: imports are at the top, there are no panics, and the test names are fine.
- The PR title and labels (`bug`, `ty`) match the AGENTS.md guidance.

**Verdict:** Good fix with focused tests. I'd suggest hoisting the invariant check and adding a generic or final-subclass overload test as follow-ups.
