# REVIEW A

## Review of #22136: Align cached HTTP policies within the payload buffer

**Caveat:** `gh pr diff` output was truncated in the middle. I reviewed the format and validation code in the merged checkout, in `crates/uv-client/src/cached_client.rs`. I did not see the new and changed tests in the diff beyond the `torn_policy_is_refetched` hunk and the `into_data` call-site changes. I did not build or run anything.

### Summary
The PR changes the cache entry layout to `payload | zero padding to 16 | entry ID (16) | archived policy | CRC32 | u64 len`. The policy now sits at a 16-byte-aligned offset in the same `AlignedVec` as the payload. Reads borrow the policy in place through `cache_policy()` and hand back the same allocation through `into_data()`. This removes one allocation and one copy per cache read. The design is sound, and I found no blocking issues.

### Correctness and safety
- **The `unsafe` access looks sound.** `cache_policy()` calls `access_unchecked` on `bytes[policy_start..]`.
  - `from_aligned_bytes` validates exactly that slice with `rkyv::access`. `bytes` is then truncated to `contents_len`, so the footer is not part of the slice. rkyv finds the root from the end of the slice, so including the footer would have broken this.
  - `bytes` is private, and nothing mutates it before `into_data(self)` consumes it, so the archive stays valid.
  - The `SAFETY` comment states these points and uses `#[expect(unsafe_code)]`, as AGENTS.md asks.
- **Validation is correctly scoped.** `rkyv::access` runs on `policy_bytes` only, not the whole buffer. Relative pointers therefore cannot reach into the payload, entry ID, or footer. The test that moves the payload boundary into the policy's strings and recomputes the CRC covers this attack.
- **Padding and bounds.**
  - `padding_len` is computed from the untrusted `data_len`, but every slice step uses `.get()` and returns an error on failure, so there is no panic path.
  - The padding is covered by the CRC in both `serialize_policy` and the reader. The reader does not check that padding is zero, but the CRC already catches changes.
- **`refresh_policy` is consistent with the new layout.** It seeks to `policy_start - 16`, re-checks the entry ID, rewrites the tail from `policy_start - 16` onward, and sets the length to `policy_start + tail.len()`. The padding depends only on `data_len`, which a refresh never changes, so it stays valid.
- **Alignment.** The entry ID starts at a 16-byte-aligned offset, so `policy_bytes` starts aligned. The buffer is `AlignedVec<16>` in both `from_path_sync` and `from_reader`. rkyv's own validation also rejects misalignment, so a mistake here would fail safely.

### Issues and suggestions
1. **On-disk format change.**
   - Entries written without padding will fail the CRC and be refetched. This is safe, but the CRC failure also blocks offline use of those entries.
   - Please confirm the cache bucket or version bump is handled for 0.13, since the PR says it reapplies #22079 for that release. If it isn't, old entries stay unusable until they are replaced.
2. **`into_data` keeps the extra capacity.** `resize(data_len, 0)` shrinks the length but not the capacity, so each payload holds the tail's bytes (policy, up to 15 bytes of padding, ID, footer). That is small, but long-lived payloads such as archive pointers keep it. A comment noting this is intentional would help. `shrink_to_fit` would defeat the purpose by reallocating.
3. **Panic path in `serialize`.** `.expect("IDs have 16 bytes")` is probably pre-existing, but AGENTS.md says to avoid `expect` and `unwrap`. Mapping the failure to an `ErrorKind::ArchiveWrite` error would be cleaner.
4. **`bytes.resize(contents_len, 0)` in `from_aligned_bytes`.** It is only a truncation, so it never zero-fills. `truncate`, if `AlignedVec` offers it, states that intent more clearly. If it only offers `resize`, this is fine.
5. **Repeated error strings.** "invalid HTTP cache payload length" appears three times, for three different failures: `usize` conversion, `data_len` out of range, and padding or entry ID out of range. Distinct messages would make corrupt caches easier to debug.
6. **Hard-coded offset in a test.** `torn[data_len.next_multiple_of(16) + 16]` hard-codes the layout. A small helper or a constant for the policy offset would stop it from silently drifting if the format changes again.

### Performance
Skipping the separate allocation and copy per read is a clear win. The cost is at most 15 padding bytes per file plus the unchanged CRC pass. Nothing in the diff I could see is a concern.

### Tests
- The tests I could see cover torn policies, payload-boundary pointer attacks, and growing and shrinking the policy in place. They use the same style as the existing tests.
- I could not check from the truncated diff whether there is a test for an entry with `data_len % 16 == 0` (zero padding). There should be one, alongside the unaligned `1024 * 1024 + 7` case.
- I also could not check whether there is an old-format-entry-is-refetched test. If the format version isn't bumped, that test matters.
- Please check whether any of the new tests need a `#[cfg(feature = "test-...")]` gate, as AGENTS.md requires.

**Verdict:** Looks good to merge. The main follow-up is to confirm how old-format entries are handled.

## Summary
The PR pads the payload to a 16-byte boundary so the entry ID and archived policy start aligned inside the same `AlignedVec`. The policy is then read in place with `access_unchecked`, and `into_data()` hands the original allocation back to the caller. This removes one allocation and one copy per cache read. The change is well scoped, and the format and invariants are documented clearly.

## Correctness
- **Alignment:** `padding_len` makes `entry_id_start` a multiple of 16. The 16-byte entry ID then leaves `policy_start` aligned too. The buffer base comes from `AlignedVec<16>`, so the alignment holds. `payload_and_policy_share_an_aligned_buffer` checks this for `data_len` 0..32.
- **Validation scope:** `rkyv::access` runs only on `policy_bytes`, so relative pointers can't reach into the payload, entry ID or footer. `policy_pointers_cannot_reference_the_payload` tests this well. It recomputes the checksum so the rejection comes from rkyv and not the CRC.
- **Checksum coverage:** Padding is now part of the CRC in both `serialize_policy` and the read path. The existing `cache_trailer_corruption_is_rejected` test loops from `b"payload".len()`, so it covers the padding bytes too.
- **`refresh_policy`:** It seeks to `policy_start - 16`, which is the entry ID. It keeps the ID check, then writes the tail and calls `set_len(policy_start + tail.len())`. This matches the old `data.len() + 16 + tail.len()` once padding is counted. The rewritten length and offsets look right. The padding stays untouched and still matches the CRC, since the `data_len` input to `serialize_policy` is unchanged.
- **Unsafe block:** The `SAFETY` comment is sound. The fields are private, `bytes` is only mutated in `into_data`, and that method consumes `self`. `#[expect(unsafe_code)]` follows the repo guidelines.

## Issues and suggestions
1. **On-disk format change.** Any entry written without padding, such as one from #22078 or an earlier layout, will have a different CRC input whenever `data_len % 16 != 0`. It will fail validation and be refetched. That is acceptable if the cache bucket version is bumped, or if the earlier layout never shipped in a release. The PR says it "reapplies #22079 for 0.13", which suggests the second case. Please confirm in the description. If the layout did ship, the cost is a one-time refetch of those entries.
2. **Panic-capable slicing.** `&self.bytes[self.policy_start..]` in `cache_policy()` can panic if the invariant is ever broken. The `from_aligned_bytes` bounds checks make that unreachable today. A `debug_assert!(policy_start % 16 == 0 && policy_start <= bytes.len())` at construction would make the invariant explicit, since the unsafe code relies on it.
3. **Repeated magic expression.** `AlignedVec::<16>::ALIGNMENT` is used in several places, and the `next_multiple_of(16)` literals appear in the integration tests. A small shared constant or helper would keep the tests from drifting from the implementation. The tests can't call the private `padding_len`, so a `pub(crate)` const would help.
4. **Missing tests.** The tests would be tighter with two additions:
   - A test that `from_aligned_bytes` rejects an entry where `data_len` falls inside the padding region, so the tail is shorter than the padding. The `tail.get(padding_len..)` error path is untested.
   - A check that policies larger than the payload (`x-large`) still round-trip for `data_len % 16 != 0`. `policy_can_grow_and_shrink_in_place` partly covers this with `+ 7`.
5. **Style nits.** The tests use `assert!`/`assert_eq!`, which matches the neighbouring tests. Insta isn't needed for byte-level checks. The new code uses fully qualified `rkyv::access::<…, rkyv::rancor::Error>` twice. A top-level `use rkyv::rancor::Error as RancorError` would follow the "prefer top-level imports" guidance.
6. **Minor wording.** The "invalid HTTP cache payload length" message is reused for the padding and entry-ID bounds failures. That is fine, but a distinct message such as "truncated padding" would help when debugging corrupt entries.

## Performance and security
- **Performance:** The allocation and memcpy of the policy are gone from the hot read path. The cost is at most 15 padding bytes per entry, plus a few bytes hashed.
- **Security:** Treating cache files as untrusted is handled well. The CRC is checked before rkyv validation. Validation covers only the policy slice. Only validated bytes reach `access_unchecked`.

## Verdict
This looks correct and well tested. I'd like the format-compatibility note from item 1 and the `debug_assert` from item 2. The other items are optional polish.
