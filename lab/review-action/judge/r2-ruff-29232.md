# REVIEW A

## Review of #29232: release closed-file ASTs in more language server operations

Overall this is a small, coherent change. `ParsedModuleGuard` replaces the hand-rolled "clear if closed" snippet in `symbols_for_file_global_only` and applies it to the other whole-workspace scans. I found no blockers. These are the points I'd raise, most important first.

### Non-blocking issues

1. **No test coverage (`parsed.rs`).** The PR says it relies on existing tests. Those tests only check that results are unchanged, so nothing checks the new behavior: a closed file's AST is cleared after the guard drops, and an open file's AST is kept. `AGENTS.md` asks for focused tests on semantic changes. A small `ruff_db` unit test would cover it. It could load via `load_then_clear_on_drop` on a closed file and an open file, drop the guard, and check whether the module is still cached. The cached state would need a test-only accessor, or `heap_size` could be used.

2. **`implementations_for_file` returning `Option<Vec<_>>` (`ide_support.rs`).** `None` and `Some(vec![])` mean "skipped" and "searched, nothing found". The only reason to distinguish them is to avoid creating the guard in the caller. The cost is that the type now carries a distinction most callers don't care about.
   - Alternatives are a separate cheap predicate such as `may_have_implementations(db, file)`, or putting the guard inside `implementations_for_file`.
   - If you keep the `Option`, the doc comment is clear. I'd still prefer one of the alternatives.
   - `goto_implementation` still creates the guard for `Some(empty)`, which can re-parse an evicted AST just to clear it again.

3. **Guard created after the AST was already loaded (`goto_implementation.rs`).** `implementations_for_file` loads and uses the AST internally without clearing it. The guard is created afterward. The AST is usually still cached, so the second load is cheap. But the comment, "release closed files' ASTs as we go", hides that the guard doesn't cover the search itself, only the target conversion. Creating the guard before the search would be more robust and would match `direct_subtypes`.

4. **`clear_on_drop` is decided at load time.** If a file is opened between load and drop, its AST is cleared anyway. This is harmless, since the AST is reparsed on demand, and it is the same as the old behavior. It could be noted in the doc comment.

5. **Guard in a tracked query (`symbols_for_file`).** Clearing the `ArcSwap` inside a Salsa query is the same pattern as before for `symbols_for_file_global_only`.
   - It is now also in `symbols_for_file`, which backs other IDE features (document symbols and similar) as well as workspace symbols.
   - Closed files in those paths now get re-parsed on later requests. The comment mentions only workspace symbol searches. Please confirm that no per-request, single-file caller is hurt, or tighten the comment.
   - The PR already links ty#3909 for the broader trade-off.

### Nits

6. **`Deref` to `ParsedModuleRef`.** Callers now write `module.syntax()` through two derefs. This works, but `ParsedModuleGuard` isn't `Clone` and can't be passed where a `&ParsedModuleRef` is stored. That's fine for now. `#[must_use]` on `load_then_clear_on_drop` would catch accidental `let _ = ...`. That would drop the guard immediately and clear the AST before use.

7. **`_ast_guard` in `direct_subtypes` and `goto_implementation`.** The comments explain why the guard is kept alive. Naming the binding `_ast_guard` is correct, since a bare `_` would drop it at once.

8. **Moving `class_literal_to_hierarchy_info` into `direct_subtypes`** is reasonable. It is needed so the guard covers range collection. The doc comment on `direct_subtypes` ("Finds classes that directly inherit…") should be updated to say it now returns hierarchy info.

### Security and performance

- There are no security concerns. The change only affects cache lifetime.
- Performance: it trades cache hits for lower memory and fewer pauses on database updates. Repeated references or rename requests will reparse closed files. The PR acknowledges this and links the tracking issue.

# REVIEW B

**Review of PR #29232: release closed-file ASTs in more language-server scans.** The PR is already merged, so these points are for follow-up. I read the diff only and did not build or run anything.

**Overall:** The change is small and consistent. It replaces the ad-hoc `parsed.clear()` pattern with an RAII guard, so the AST is also released on early returns and panics. The approach looks sound.

**Potential bugs and risks**

1. **Guard lifetime versus `Deref` and `module()` (non-blocking).**
   - `ParsedModuleGuard` derefs to `ParsedModuleRef`, and `Drop` calls `self.module.module().clear()`.
   - The `ParsedModuleRef` handles that callers copy or derive from the guard keep the AST alive. `ArcSwap::store(None)` only drops the cache's own reference, so memory is freed when the last handle goes.
   - Any result that borrows from the AST and outlives the guard is unaffected. It just delays the free.
   - The comments say the guard must stay alive "through target conversion". That is correct, but nothing enforces it, so it is easy to break later.

2. **`symbols_for_file` is a `#[salsa::tracked]` query (non-blocking).**
   - Clearing the AST inside a cached query is fine for correctness, because the result is memoized.
   - Open files are skipped, so editor requests still keep their AST.
   - The cost is that a later non-scan consumer of a closed file, such as a diagnostics or hover request, reparses it. The `load_then_clear_on_drop` doc comment mentions the cache-efficiency tradeoff, and the linked issue is tracking a better solution.

3. **`is_file_open` is evaluated at load time, not at drop time (minor).**
   - If a file is opened between the load and the drop, for example in a parallel scan on a snapshot, the AST is still cleared.
   - This is harmless, because the next request reparses it.
   - It also means a file that was closed when loaded and has been reopened still gets cleared. The doc comment says "closed when loaded", so this is documented.

4. **Redundant `is_file_open` lookups (minor performance).**
   - `load_then_clear_on_drop` calls `db.system().is_file_open(path)` for every file.
   - In `goto_implementation` and `direct_subtypes`, this runs once per scanned file, including files that return early.
   - The `goto_implementation` change correctly avoids loading the AST when the text matcher rules the file out. This is why `implementations_for_file` now returns `Option`.

**Code quality**

5. **Changing `implementations_for_file` to return `Option<Vec<_>>` (non-blocking, design).**
   - The `None` versus `Some(empty)` distinction exists only so the caller can skip creating a guard.
   - It leaks a performance detail into the public API.
   - A cleaner option is to have the guard created inside `implementations_for_file`. That is hard here, because the returned definitions borrow data used by the later conversion step.
   - `Option<Vec<_>>` is acceptable, but a short note on the caller side or a distinct type would be clearer. As written, `None` and `Some(vec![])` mean the same thing to the caller, which is confusing.

6. **`type_hierarchy_subtypes` change.**
   - `direct_subtypes` now returns `Vec<TypeHierarchyClass>`, so `class_literal_to_hierarchy_info` runs inside the guard's scope. This is the right fix, because that conversion can load the AST for range collection.
   - The doc comment on `direct_subtypes` still says "Finds classes that directly inherit…". If it mentions `ClassLiteral`, it needs updating.
   - `direct_subtypes` is also called from other places (not verified), which would have to be adapted as well.

7. **Repeated comments.** The same "can scan the whole project, so release closed files' ASTs as we go" comment appears at each call site. That is acceptable under the repo's "explain why" guideline, but it could be shortened to a pointer to the helper's docs.

8. **`_ast_guard` naming and drop order.**
   - A named `_ast_guard` binding is correct, because a bare `_` would drop the guard immediately.
   - A short `// must not be bound to `_`` note would prevent a future "cleanup" regression. A `#[must_use]` attribute on `ParsedModuleGuard` would also help.
   - `ParsedModuleGuard` has no `#[must_use]`, and `load_then_clear_on_drop` returns it by value. Adding `#[must_use]` on the method or the struct would catch `let _ = ...` and a discarded call.

**Test coverage**

9. **No new tests (non-blocking, but notable).**
   - The PR says it relies on existing tests. Those cover functional correctness only, not the new behavior.
   - A unit test in `ruff_db::parsed` would be cheap: load a closed file through the guard, drop it, and assert `parsed.inner` is `None` (or that a second load reparses). A second case would use an open file and assert the AST is retained.
   - That test would also protect the `symbols_for_file_global_only` refactor, which silently changed ordering. The old code cleared after the visitor ran, and the new code clears at scope end. That is semantically the same, but it is untested.

**Security:** No concerns. This only changes memory-release timing, with no new inputs or trust boundaries.

**Verdict:** The change is good. The main follow-ups are a `#[must_use]` on the guard, a unit test for the guard, and tidying the `Option<Vec<_>>` API in item 5.
