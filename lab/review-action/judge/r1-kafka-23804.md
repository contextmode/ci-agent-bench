# REVIEW A

**Review of PR #23804: KAFKA-21181, return NOT_COORDINATOR from a stale transaction coordinator cache (4.3 backport)**

The PR is already merged. This is a read-only review of the diff. I didn't build the code or run the tests. The repo has no `CLAUDE.md`, so I used general Kafka conventions.

**Summary**

`TransactionStateManager.getTransactionState` now checks `isCoordinatorFor` before it uses a cache entry. The check passes only if the local replica is the leader of the `__transaction_state` partition and its leader epoch equals the entry's `coordinatorEpoch`. If the check fails, it returns `NOT_COORDINATOR`. This closes the window between losing leadership and `onResignation` running. In that window a TV2 `EndTxn(COMMIT)` could previously get a fatal `INVALID_TXN_STATE`.

**Code quality**
- The production change is small, isolated and well commented. Putting the check in the shared lookup covers every caller: EndTxn, AddPartitions, VerifyPartitions, InitProducerId and `putTransactionStateIfNotExists`.
- Because the check sits ahead of the `createdTxnMetadataOpt` branch, no new entry is created in a stale cache. `testInitProducerIdReturnsNotCoordinator…` covers this.
- Using `getLeaderEpoch` as the "coordinator epoch" matches how the epoch is assigned on load. A newer epoch with the partition not yet reloaded correctly returns `NOT_COORDINATOR`, and the unit test covers that case.

**Potential issues**
1. **Race (minor, and inherent).** The leadership check and the cache read are not atomic. Leadership can change right after the check passes. The append path still fences on the coordinator epoch, and `testNotCoordinatorIfLeadershipLostBeforeAppendCompletes` covers that. This is acceptable, but a short comment saying so would help.
2. **Leader without a `Partition` object.** `onlinePartition` returns `None` for offline or unknown partitions, so `exists` is false and the result is `NOT_COORDINATOR`. That is the right answer, but it is not tested.
3. **Cost.** Each lookup now does a `replicaManager.onlinePartition` map lookup, which is cheap, and it runs inside the existing `readLock`. I don't expect a measurable effect, but the hot EndTxn and AddPartitions paths now do an extra lookup on every call.
4. **Epoch type.** `partition.getLeaderEpoch` is an `int`, so there is no overflow or boxing problem.

**Security**
No concerns. The change makes the coordinator more conservative.

**Test coverage**
- Coverage is good: six new tests cover the manager, the append-completion race, and EndTxn, Verify, AddPartitions and InitProducerId through the coordinator.
- Test mocking is more elaborate than it needs to be. The `Answer`-based `Partition` mocks are duplicated between `AbstractCoordinatorConcurrencyTest` and `TransactionStateManagerTest`. Creating real `Partition` objects or using a small shared helper would remove the duplication.
- In `testInitProducerIdReturnsNotCoordinator…`, the line that resets `leaderEpochOf` just before the final assertion is easy to miss. A comment would make it clearer.
- In `AbstractCoordinatorConcurrencyTest`, `leaderPartitions` is keyed only by `leaderEpoch`, so the mocks are shared across partitions. That works for the current tests, but it could cause confusion if a test later needs per-partition behavior.
- The `onlinePartition` default in `AbstractCoordinatorConcurrencyTest` still returns a fresh mock when `leaderEpochOf` is `None`. That mock's `isLeader` is false, so other subclasses of that test now see `NOT_COORDINATOR`. I'd check that no other subclass relies on the old behavior. The author reports `kafka.coordinator.transaction.*` passes, but the group coordinator concurrency tests also extend this base class. I couldn't confirm they were run.

Approve. The fix is correct and well tested. The suggestions above are non-blocking.
