# REVIEW A

**Review of godotengine/godot#118822: Defer resolving node path properties until inherited scene is fully instantiated**

The PR is already merged, and the approach is sound.

**Summary:** `SceneState::instantiate` now delegates to a private `_instantiate`. The `_instantiate` function takes an optional out-parameter, `r_parent_deferred_node_paths`. When a scene inherits from a base scene, the base's deferred NodePath properties are pushed into the outer scene's list. They are resolved once, in the outermost call, after all scripts are attached. This fixes #86970, where C# created node instances that were disposed later when the script attached.

**Correctness**
- Ordering looks right. The base scene's entries are appended before the derived scene's own deferred entries are processed, because the base is instantiated first. The derived scene's overrides therefore still win for the same property. The `dnp.base` is an ObjectID, and the `ObjectDB::get_instance` check covers base nodes that were freed in between.
- The nested-instance case seems fine. Only the inheritance path (`base_scene_idx`) passes `&deferred_node_paths`. Other instanced child scenes still go through the public `instantiate` and resolve their own paths at the end of their own call. This behaviour is unchanged. Instanced children may be tied to a script on a parent node, but that case isn't what this PR targets.
- One subtle point: a base scene's NodePath resolution now happens after the derived scene has applied its own property overrides and added its own nodes. A path that used to fail to resolve may now succeed, because nodes added by the derived scene exist. A path that used to resolve to a base node that the derived scene later removes or replaces would now resolve differently. Both are arguably more correct, but they are a behaviour change worth a release note.
- Failure paths: if the derived `_instantiate` returns `nullptr` early (the `ERR_FAIL` paths), the bubbled entries are dropped. That is harmless, since nodes are freed anyway.

**Code quality**
- Most of the diff is re-indentation of the resolution block into an `else` branch, which makes the diff hard to read. Extracting it into a helper such as `_resolve_deferred_node_paths(...)` would keep the diff small and avoid the deep nesting. A `return`-early-style structure would also work.
- The `friend class` declarations in both directions plus the `private:`/`public:` toggling in the middle of the class are somewhat awkward. Declaring `_instantiate` in the private section at the top would be tidier. It's also worth checking whether `PackedScene` really needs `friend class SceneState`, since `SceneState::_instantiate` calls `PackedScene::_instantiate`. `PackedScene` calling `SceneState::_instantiate` needs the reverse friend, and it is already there.
- The bubbling loop can be replaced with `append_array` if `LocalVector` provides it, rather than a push_back loop. This is minor, and it also lets you reserve capacity.
- The underscore-prefixed method name `_instantiate` matches the Godot convention for private helpers. However, `PackedScene` is bound to scripting, so check that no `_instantiate` virtual or method name clashes with it. I didn't see a conflict.

**Performance**
- The only added cost is copying `DeferredNodePathProperties` entries, which hold Variants, up the inheritance chain. Each entry is copied once per inheritance level. This is negligible compared with instantiation itself. `std::move` semantics could avoid the Variant copies, but it isn't worth worrying about.

**Security:** No concerns. There are no new inputs or parsing, and object lookups still go through ObjectDB validation.

**Test coverage**
- The diff has no tests, which is the main gap. The bug is C#-specific, but the engine-level behaviour is testable in `tests/scene/test_packed_scene.h` (or similar) without C#:
  1. Create a base scene with a node that has a NodePath-to-Node property (e.g. a custom exported property or `Node`-typed property on a test class), and an inherited scene.
  2. Verify that the property resolves to the right node in the inherited instance.
  3. Verify that the property resolves to a node added by the derived scene (new behaviour), and that array and dictionary properties work through inheritance.
- A regression check that the base scene's resolution is deferred, such as a setter that records call order relative to `set_script`, would also pin the fix down.

**Verdict:** The change is correct and minimal in behaviour. I'd suggest a follow-up that extracts the resolution block into a helper and adds a unit test for inherited scenes with node-typed properties.

# REVIEW B

# Review of PR #118822: Defer resolving node path properties until inherited scene is fully instantiated

This PR is already merged, with approvals from KoBeWi and bruvzg. I read the diff only and did not build or run it. The repo has no CLAUDE.md, so I judged style against Godot's usual conventions.

## Summary
The PR fixes #86970. When a scene inherits from another, the base scene used to resolve its `NodePath`-backed properties (Node-typed exports, arrays and dictionaries) inside its own `instantiate()`. That happened before the inheriting scene had attached scripts to the nodes. In C# this created wrapper instances that were then disposed when the script was attached, which left stale references.

The fix adds a private `_instantiate()` that takes an out-parameter, `r_parent_deferred_node_paths`. A base scene instantiated through inheritance pushes its deferred entries up to the caller instead of resolving them. Only the outermost `instantiate()` resolves them, after all scripts are attached.

## Correctness
- **Ordering:** Base-scene entries are pushed to the caller's `deferred_node_paths` at the end of the callee, after the callee has added its own entries. The caller's own entries are appended afterwards, so base properties are set first and derived overrides last. This matches the old behaviour, where the base resolved first.
- **Path resolution:** Each entry's `dnp.base` is an ObjectDB ID and its value is a path relative to that base. The relative paths stay valid after the entries are moved to the outer scene. The caller's node tree is a superset of the base's, so `get_node_or_null` should still resolve them.
- **Nested inheritance (A → B → C):** The pass-through chains correctly, because each level hands `&deferred_node_paths` to its base.
- **Failure paths (to verify):** There are early `return nullptr` paths in the middle of `_instantiate`, for example `ERR_FAIL_NULL_V` and stray-instance cleanup. If the base succeeds but the derived scene fails afterwards, the bubbled entries are dropped. That seems fine, because the nodes are freed and the entries would resolve to nothing. I'd still check that nothing leaks.
- **Behaviour change (to verify):** Between the base's instantiation and the outer resolution, base nodes no longer have their node-path properties set. This covers the base scene's own `_init`, notifications, and any setters triggered while the derived scene applies its overrides. Code that read those properties during that window, for example a derived scene overriding a property and relying on the base's value already being resolved, would now see null. This is the intended trade-off, but it is worth a release note.

## Code quality
- **Diff size:** The diff looks larger than it is, because the resolution loop moved into an `else` block and was re-indented. Splitting the resolver into a helper, for example `_resolve_deferred_node_paths(...)`, would have kept the diff small and avoided the extra nesting.
- **Duplicated wrappers:** `SceneState` and `PackedScene` now each have an `instantiate` wrapper and a private `_instantiate`, joined by mutual `friend` declarations. This works, but it is a bit heavy. `_instantiate` is also a name Godot normally uses for virtual methods, so it could be confusing.
- **Copying entries:** `push_back(dnp)` copies each entry, including the `Variant` value. Using `append_array` or moving the entries would avoid that. The cost is negligible here.
- **Access specifiers:** The `private:`/`public:` toggling in the middle of the class breaks up the declaration order in `packed_scene.h`. Grouping the private helpers together would be tidier.

## Performance
There is no meaningful change. The same work happens, just later, and a vector copy is added per inheritance level.

## Security
I found no concerns.

## Test coverage
The diff includes no tests. This area is testable, since `tests/scene/test_packed_scene.h` and similar files exist. Useful cases:
- A scene inheriting a base that has a Node-typed export, an `Array[Node]` export and a `Dictionary[Node, Node]` export, with all of them resolved correctly after instantiation.
- Three-level inheritance, where the derived scene overrides a base property.
- A check that a script attached by the derived scene sees the final node instance, which is the original bug. This is hard to cover without the C# module, but a GDScript setter that records the node it receives could approximate it.

## Verdict
The approach is sound, minimal and behaviour-preserving for the normal case. I'd suggest adding a regression test and extracting the resolver into a helper.
