# REVIEW A

**Review of PR #65129: Fix `shift-enter` in search bar for JetBrains keymap**

The PR is already merged, with one approval. Overall it is a small, well-scoped fix.

**What it does**

The macOS and Linux JetBrains keymaps change the context from `BufferSearchBar` to `BufferSearchBar && !in_replace > Editor`. That makes the binding more specific than `Editor && mode == auto_height`, so it wins precedence. A regression test is added.

**Keymap change**
- I haven't run the code. The approach is reasonable: Zed resolves precedence by context depth, so the `> Editor` descendant form beats the shadowing binding.
- `!in_replace` correctly leaves Shift-Enter alone in the replace field, where `NewlineBelow` or the default is probably what you want. One check: `in_replace` is set on the replace editor's context, so `BufferSearchBar && !in_replace > Editor` should parse as `(BufferSearchBar && !in_replace) > Editor`. In Zed's context grammar, `>` binds loosest, so I'd expect `in_replace` to be evaluated on the `BufferSearchBar` node rather than on the `Editor`. If `in_replace` is a key on the `Editor` context instead, the `!in_replace` would be checked against the wrong node. The test only exercises the query editor, so the replace-field behavior is untested. Please confirm where `in_replace` is set. A second test for the replace field would settle it.
- The Windows and other JetBrains keymaps, if any exist, were not touched. Please check that no other `jetbrains.json` variants carry the same bug.

**Test**
- It is a useful regression test. It loads the default keymap and then the JetBrains keymap in the same order as production, so precedence is exercised properly. It also asserts that no newline is inserted and that the match index wraps from the first to the last match.
- It duplicates the keymap-loading logic from `load_default_keymap`. If that function changes, the test can drift. Extracting a shared helper would be better, but that is optional.
- It uses `.unwrap()` and `.expect()` inside the `add_window` closure. Tests commonly do this and it is acceptable. CLAUDE.md discourages `unwrap()`, so the `.unwrap()` calls on `load_asset_allow_partial_failure` could be `.expect("...")` for clearer failures.
- It only covers the macOS/Linux-agnostic path. `DEFAULT_KEYMAP_PATH` and `BaseKeymap::JetBrains.asset_path()` are platform-dependent, so the test runs against whichever keymap the host OS selects. That is fine, but CI on one platform will not catch a regression in the other platform's JSON.
- There is no coverage for the replace-field case, as noted above.

**Style and CLAUDE.md**
- The test's comments explain *why* the keymaps are loaded in a particular order, which fits the guidelines.
- I didn't see any PR-hygiene issues. The title uses a `keymap:` prefix, which is allowed. The Release Notes section is present and its bullet uses "Fixed".
- The `README.md` `> [!IMPORTANT]` marker rule in CLAUDE.md applies to agent-authored changes. This PR was authored by a human, so it doesn't apply.

**Performance and security**
- No concerns. This is a keymap context tweak and a test.

**Verdict:** Good fix. The main follow-up is to verify the `in_replace` context scoping and ideally add a replace-field test.

# REVIEW B

**Review of PR 65129: keymap: Fix `shift-enter` in search bar for JetBrains keymap**

The PR is already merged and approved. These are my notes.

**What it does**
- It changes the JetBrains keymap context from `BufferSearchBar` to `BufferSearchBar && !in_replace > Editor` on macOS and Linux.
- Shift-Enter in the query field now resolves to `search::SelectPreviousMatch`. Before, the `Editor && mode == auto_height` binding for `NewlineBelow` shadowed it.
- It adds a regression test.

**Correctness**
- The context is more specific, so it should win over the `Editor && mode == auto_height` binding when the query editor is focused. The test checks exactly this.
- `!in_replace` keeps the replace field on `NewlineBelow`, or whatever binding the user's keymap gives it. This looks intentional.
- The `>` descendant operator means the binding applies only while the focused element is an `Editor` inside the `BufferSearchBar`. A non-editor focus inside the bar, such as the toggle buttons, no longer triggers `SelectPreviousMatch`. Previously the plain `BufferSearchBar` context did. That is a small behavior change, probably harmless, since shift-enter on a button would normally activate the button.
- I haven't verified that `in_replace` is set as a key context on the replace editor's ancestor chain. It's worth confirming that `!in_replace > Editor` is parsed the way the author expects: `!` applies to `in_replace` on the parent node. The test only covers the query editor, not the replace field.
